# Swiver 순차 CPU·74 회로·CPLD 분할 연구노트

작성일: 2026-10-23. 대화 범위: 이전 뷰어 세션의 종료 지점부터, 순차 실행 정리·74 비교 회로·CPLD 자원 및 재고 조사·실제 fit 탐색·ATF1502 필요성·ROM 없는 FSM 축소 논의까지.

이 문서는 **대화의 진행과 실험 결과를 보존하는 연구 기록**이다. 정본 ISA나 하드웨어 사양을 교체하지 않는다. 문서화 직전 저장소 기준 커밋은 `6eb091a`다. 수치의 의미와 검증 경계를 함께 남겨, 실패한 후보의 칩 수가 완성 CPU의 BOM으로 재사용되거나 실험 후보가 정본으로 오인되는 것을 막는다.

질문 인용은 이 대화에 표시된 사용자 발화를 따른다. 수치와 구현 설명은 현재 파일을 다시 읽어 확인했다. 초기 세션의 전체 축어록을 복원한 기록은 아니며, 모든 중간 답변이나 실행 로그를 빠짐없이 전사한 것도 아니다. 과거 테스트 결과는 추적된 문서·증거 파일에 기록된 결과이고, 이번 문서화 작업에서 전체 테스트와 fitter를 재실행한 것은 아니다.

## 1. 출발점: 회로 뷰어에서 CPU 전체 검증으로

이전 세션의 마지막 작업은 루트 README에 Windows 실행 방법을 추가하는 것이었다. 일반 실행, 자동 리로드, 포트 변경, 가상환경 직접 실행과 활성화, 백그라운드 실행·로그·종료, 테스트와 CPU 예제·내보내기를 정리했고 `1ddc504`로 커밋되어 있었다.

이후 사용자는 “vhdl이나 verilog 같은거 sim 만들거나 있는거 써서 alu랑 데이터패스, 제어경로가 다 작동하는지 확인”할 수 있는지 물었다. 이어 어떤 부분을 74로 만들고 어떤 부분을 CPLD·FPGA·ROM으로 대체할지 판단하려 했다. 질문의 목적은 HDL 언어를 사용하는 것 자체보다 **현재 ISA를 실행하는 전체 회로를 비교할 수 있는 근거를 만드는 것**이었다.

작업은 다음 검증 층으로 나뉘었다.

| 검증 층 | 확인할 수 있는 내용 | 대신 증명하지 못하는 내용 |
|---|---|---|
| 순차 기능 CPU | 명령 결과, 메모리 의미, 논리적 SYS 수 | 물리 핀·CPLD fit·보드 속도 |
| 74 부품 연결 모델 | 게이트 및 레지스터 연결, 버스 동작, 기준 CPU와 실행 비교 | ns 지연·클록 skew·실물 배선 |
| 생성 CUPL 및 vendor fit | 해당 장치·패키지에서 논리와 핀 수용 | 전체 보드 전기적 동작 |
| 생성 CUPL 식의 클록 에지 모델 | 제어 출력과 외부 래치·74 ALU의 기능적 통합 | post-fit 지연 시뮬레이션 |
| 실제 보드 검증 | 전원·리셋·부하·setup/hold·실효 클록 | 이 대화에서는 아직 수행하지 않음 |

구현된 비교 체계는 Python 회로 모델과 생성 CUPL을 사용한다. VHDL/Verilog로 전체 CPU를 완성했다고 기록하지 않는다.

## 2. 순차 실행 계약 확인과 문서 반영

사용자는 “이전 세션에서 정직한 in order로 실행하게 바꾸기로 했는데” 문서에 반영되었는지 확인하고, 업데이트·커밋·푸시를 요청했다. 여기서 in-order는 단순히 완료 순서만 지킨다는 뜻이 아니라, **한 명령을 끝낸 다음에 다음 opcode를 인출하는 비중첩 실행**으로 구체화되었다.

현재 [순차 CU 계약](../../../reference/hardware/cpld-sequential-cu.md)은 다음을 명시한다.

- 명령과 데이터는 하나의 매핑된 64 KiB 주소 공간과 공유 버스를 사용한다.
- RAM 실행을 허용하며 Boot/Run 메모리 매핑을 유지한다.
- 피연산자 인출과 실행을 겹치지 않는다. 이전 IF/EX 겹침과 분기 버블을 현재 실행 비용으로 사용하지 않는다.
- WAIT는 진행을 멈추지만 메모리/MMIO 부작용을 중복 실행하지 않는다.
- ISA, 플래그 의미, RAM의 반환 스택 포인터와 CALL/RET 접근 순서를 유지한다.

이 정리는 `93df290`에 연결된다. 이후 하이브리드 모델은 이 ISA 결과와 메모리 접근 순서를 유지하지만, 공통 바이트 버스의 여러 물리 전송을 도입했다. 따라서 **하이브리드 전송 tick과 정본 기능 모델의 SYS는 같은 단위가 아니다.** 이 차이는 성능 비교 전체에 적용된다.

## 3. “돌려봤어요?”: 성능 수치의 기준

사용자는 실제 실행 여부와 실효 MIPS를 물었다. 비교에서 구분해야 할 값은 호스트 Python 실행 속도, 모델의 명령당 SYS/tick, 가정 클록으로 환산한 native MIPS, 실물에서 측정한 MIPS다.

[74 모델 README](../ttl/README.md)에 기록된 순차 프로그램 비교 결과는 다음과 같다. MIPS 분자는 HALT/TRAP을 제외한 native retirement이고, 분모는 종료 HALT까지의 모든 SYS다.

| 프로그램 | SYS | 유효 native 명령 | **가정** 2 MHz에서 MIPS |
|---|---:|---:|---:|
| 반복 Fibonacci → 233 | 504 | 159 | 0.631 |
| 재귀 Fibonacci(3) | 379 | 106 | 0.559 |
| 재귀 Fibonacci(8) | 5,689 | 1,632 | 0.574 |
| ADD 4,096회 | 12,290 | 4,096 | 0.667 |
| CALL/RET 256쌍 | 4,098 | 512 | 0.250 |

환산식은 `native MIPS = 유효 명령 수 / 총 클록 수 × 클록 Hz / 1,000,000`이다. 표는 회로가 2 MHz를 만족한다는 증거가 아니다. 프로그램의 명령 구성, CALL/RET 빈도, WAIT가 달라지면 CPI와 MIPS도 달라진다.

사용자는 타이밍 때문에 74 대신 CPLD·FPGA·테이블 ROM이 필요한 부분도 물었다. 이 대화에서 기능 모델은 실제 경로의 ns 지연, 버스 부하, 배선 길이, 메모리 지연, setup/hold를 모두 포함하지 않았다. 따라서 특정 블록을 “74로는 불가능하므로 반드시 교체”해야 한다는 결론은 확정하지 않았다. 칩 수 감소, 기능 검증, 최고 동작 클록은 서로 다른 판단 항목이다.

## 4. 74로 먼저 완성한 비교 회로

“74로 sim을 완성해보고 비교해보죠?”에 따라 제어와 데이터경로를 74HC 기능 연결로 만든 별도 후보가 추가되었다. `e86db32`가 이에 해당한다.

모델은 opcode마다 Python으로 정답 동작을 수행하는 방식이 아니라, 구축된 게이트와 부품 진리표를 평가하고 모든 D를 같은 에지에서 샘플한다. 기존 ALU의 153×8, 283×2, 157×2는 유지한다. 메모리 접근은 회로가 만든 주소·선택·RD/WR·버스 신호를 소비한다.

| 기본 74 후보의 그룹 | 패키지 수 |
|---|---:|
| 제어 | 55 |
| 스택 임시 상태·계산·검사 | 43 |
| 주소·PC 입력 경로 | 34 |
| 일반 레지스터·입력 MUX | 18 |
| ALU 코어 | 12 |
| ALU 제어·Z 판정 glue | 4 |
| 데이터 버스 경로 | 11 |
| 메모리 선택 | 8 |
| 합계 | **185** |

이 185개는 메모리 IC·전원·클록·리셋·추가 부하 버퍼를 제외한 단순 gate 구현이다. 최소 BOM이 아니다. 관측용 trace 출력과 진단 상태도 포함되어 있다.

사용자가 “최적화 하면 몇개”인지 물었을 때 진행한 1차 gate/package 최적화는 `b8c1e4e`다. 상수 MUX 변환, 공통식 공유, dead gate 제거, 채널 및 574 재배치로 174개가 되었고, AND tree를 HC11/21로 치환하여 **167개**가 되었다. 185개 대비 **18개, 약 9.7% 감소**다. 574는 14→12개, 157은 65→56개였다.

이는 논리와 SYS를 유지한 최적화이며, 디코더·카운터로의 대규모 구조 변경이나 임시 레지스터 재사용까지 탐색한 최소값은 아니다. 사용자는 곧 “CPLD나 그런거 쓰면 얼마나 줄어드는지가 궁금”했다고 정정했다. 이후 논의의 중심은 gate-only 최적화에서 **CPLD를 포함한 실제 전체 구성**으로 이동했다.

## 5. 잘못된 칩 수 비교를 정정한 구간

사용자는 “RAM이나 레지스터 때문에” 부품이 많은지, 데이터패스도 CPLD에 넣기로 한 것 아닌지, 제어·검사 게이트가 왜 외부에 남는지 반복해서 확인했다.

핵심 문제는 all-74 모델의 기능 그룹을 빼는 계산을 하이브리드 BOM처럼 해석하는 것이었다. 과거의 **130/87/16**은 모델 그룹의 단순 차감 수치이며, 실제 CPLD 통합 후 잔여 칩 수가 아니었다. [통합 구현 감사](../../../reference/hardware/cpld-integration-audit.md)와 `70b9508`은 이를 정정했다.

RAM IC 자체만으로 185개가 된 것도 아니다. 그 집계에는 메모리 IC가 제외되어 있고, 큰 비중은 제어 디코드, 다음 상태, 데이터 선택 MUX, 주소 산술, 스택 임시 상태와 검사에 있었다. 하이브리드에서는 CPLD에 넣은 제어 기능을 외부 74 게이트로 다시 더하면 안 된다.

또한 다음 두 가지를 구분했다.

- 스택 정렬·범위·overflow/underflow를 검사하고 잘못된 쓰기를 막는 것은 실행 계약의 기능이다. CPLD 내부로 옮길 수 있지만 무단 삭제하면 ISA 동작이 달라진다.
- 오류 코드 저장이나 trace 관측 출력은 진단 목적이 섞여 있다. 제품 회로의 필수 외부 핀과 동일하지 않다.

사용자가 요구한 답은 “CPLD는 된다고 가정했을 때 남는 부품”과 “실제로 fit되어 동작하는 후보”를 각각 계산하는 것이었다. 이후 보고에서는 가정한 수량, 실제 블록 fit, 통합 기능 검증을 분리하게 되었다.

## 6. 구매 기록과 실제 보유 CPLD 정정

사용자는 7월·8월 주문/배송 내역을 제공했다. 기록에는 ATF1504AS-10JU44, ATF1502AS-10JU44 외에 STM32F042, ESP32-S3 보드, USB-C 커넥터, 저항, 스위치, IMU, HC138, 3.6864 MHz 발진기, 브레드보드와 DIP 소켓 등이 있었다.

CPU 분할 설계에 직접 영향을 준 항목은 7월 6일 ATF1504 주문, 7월 17일 ATF1502 주문, 8월 13일 ATF1504 주문이었다. 그러나 주문 행을 단순 합산하면 안 된다. 사용자는 **ATF1504 한 개가 재고 부족으로 취소되어 ATF1502를 샀다**고 정정했다.

이 대화에서 사용할 최종 보유 조건은 다음과 같다.

| CPLD | 설계에 사용할 보유 수량 |
|---|---:|
| ATF1504AS-10JU44 | **2개** |
| ATF1502AS-10JU44 | **1개** |

재고 정정은 `8a0bd1f`에 연결된다. 주문 완료 화면의 표기보다 사용자의 취소·대체 설명을 반영한 조건이다. 이 노트는 주문번호·결제정보 전체를 다시 복제하지 않는다. 설계용 BOM, 구매 목록, 실제 보유 수량은 별도로 관리해야 하며, “모두 구매했다”는 판단은 최종 후보의 모든 부품과 어댑터까지 대조해야 한다.

## 7. 공통 8비트 hi/lo 버스 후보

사용자는 배선을 줄이면서 1504에 데이터패스를 넣는 방법과 1502 활용을 물었고, 공통 8비트 버스로 hi/lo를 전송하는 것은 이미 결정한 사항이라고 지적했다. 이에 따라 `cc50444`에서 명시적인 바이트 버스 후보를 만들었다.

첫 후보의 DP 저장 상태는 R0 8비트, PC 16비트, 임시 RP 16비트로 총 40비트다. 주소 low/high, TMP low/high, MBR, RESULT는 외부 574 여섯 개다. PC/RP 증감은 기존 12칩 ALU를 바이트별로 사용한다. 별도 16비트 가산기를 숨기거나 Python 정수 덧셈으로 대체하지 않는다.

MBR은 ALU B를 공급한다. PC 증감이 MBR을 덮어쓰기 때문에 피연산자를 읽기 전에 증감을 끝내고, 그동안 주소 래치가 실제 메모리 주소를 유지한다. RESULT 래치는 ALU 결과를 먼저 잡고 다음 전송에서 DBUS를 구동한다. ALU 결과를 R0에 바로 쓰면 A 입력 변경이 캡처 이후 hold 구간에 영향을 줄 수 있어 분리했다.

각 전송은 setup/capture/hold/release 네 tick이다. 574에 존재하지 않는 enable/reset을 가정하지 않는다.

| 첫 후보 | 조건부 IC 수 | 의미 |
|---|---:|---|
| 1504×2 + 외부 74 메모리 디코드 | 34 | CU가 한 칩에 들어간다는 전제 |
| 1504×2 + 1502 메모리 디코드 | 25 | 같은 전제, 10칩 디코더를 1502 한 개로 치환 |

위 수량에는 ALU 12, 외부 래치 6, HC14 1, 메모리 3이 포함된다. 발진기와 어댑터 등은 별도다. **후속 CU fit이 실패했으므로 25/34개를 완성 CPU 수량으로 확정할 수 없다.**

성능도 정본 SYS와 달라졌다.

| 프로그램 | 바이트 버스 후보 tick | 기준 SYS | 가정 2 MHz native MIPS |
|---|---:|---:|---:|
| 반복 Fibonacci → 233 | 10,292 | 504 | 0.0309 |
| 재귀 Fibonacci(3) | 7,568 | 379 | 0.0280 |
| 재귀 Fibonacci(8) | 114,160 | 5,689 | 0.0286 |
| ADD 256회 | 14,372 | 770 | 0.0356 |

이는 배선과 공유 연산을 우선한 첫 후보의 비용이다. 0.6 MIPS 수준의 정본 SYS 환산값과 혼용하지 않는다. 이 표에는 뒤에서 도입하는 제어 ROM의 네 읽기 tick이 아직 포함되지 않는다.

## 8. MC와 핀: 실제 fitter를 돌린 결과

사용자는 각각의 MC 사용량, 메모리 디코더를 1502에 넣었을 때 배선 절감, 핀 수, CU fit을 차례로 확인했다. 이 단계부터는 장치 정격으로 수용 가능성을 말하는 대신 생성 CUPL과 vendor fitter 결과를 사용했다.

첫 DP는 실제 fit되었고, 1502 메모리 디코더도 fit되었다. 하지만 직접 전개 CU는 실패했다. `dd94015`의 FSM은 **292개 전송 상태**, 9비트 상태 레지스터, 2비트 전송 phase를 가진다. 컴파일은 성공했으나 FIT1504는 `Design does not fit`을 반환했다.

실패 로그의 **배치 전 251 Logic Cell**은 성공 배치의 MC 사용량도, ISA 구현에 필요한 최소 MC도 아니다. 실패 보고서 하단의 불완전 `1/64`를 사용량으로 읽으면 안 된다. 사전 추정이었던 58~70 MC나 6비트 상태 주소는 이 구현에서 확인되지 않았다.

후속 `adde82e`에서는 스택 검사를 DP로 옮겼다. RP 하위 바이트를 DP에서 직접 사용하여 CU의 검사 기억 비트를 줄였다.

| 항목 | 원본 | 검사 분리 후 |
|---|---:|---:|
| DP 실제 MC | 57/64 | 61/64, fit 성공 |
| CU 배치 전 논리 셀 | 251 | 239, 여전히 fit 실패 |

이 결과는 검사 이동이 도움이 되지만 주된 병목을 해결하지는 못한다는 뜻이다. 또한 출력·전용 입력이 함께 늘어 핀도 고려해야 한다. MC 여유와 핀 여유는 별개이며, 총 MC를 세 칩 사이에서 자유롭게 합산할 수 없다.

근거: [CU 실패](cu-fit-evidence.json), [블록 fit](block-fit-evidence.json), [검사 분리](partition-fit-evidence.json). 실제 MC 기록은 이 실험 영역의 결과이며 정본 설계 보증으로 승격하지 않는다.

## 9. “검색”의 의미와 방향 수정

사용자가 fit되는 조합을 “검색”하라고 한 의도는 인터넷의 유사 사례를 모으는 것이 아니라, **로컬에서 기능 배치를 바꿔 CUPL을 만들고 fit을 반복하며 칩 수·배선을 비교**하는 것이었다. 사용자가 이를 직접 정정했다.

`b3393d7`의 로컬 탐색은 레지스터 수, ALU 통합, 제어 ROM, 검사 위치, 출력 방식을 바꾼 14개 블록 후보를 다뤘다. 이 과정에서 ALU를 CPLD에 넣는 후보도 시험했다. 사용자는 “8비트 래치는 그냥 외부 칩”, “ALU는 왜 CPLD에 넣어요?”라고 방향을 바로잡았다.

최종 유지 조건은 **기존 12칩 74 ALU + 외부 단순 저장 + CPLD 제어 분할**이다. CPLD ALU 후보가 fit되었다는 결과는 탐색 이력일 뿐, 채택안의 칩 절감으로 계산하지 않는다.

탐색 중 fitter가 성공을 반환하면서 자원 통계가 65/64로 나타난 후보도 있었다. 이를 임의로 정상 수용이라고 해석하지 않고 `resource_report_consistent=false`로 보존했다. 이후 채택 비교에 쓰인 55/53/27 MC 조합은 이 이상 통계 후보와 다르다.

## 10. 외부 래치 + 74 ALU: 세 CPLD fit 성공

`06d6110`은 R0/PC_LO/PC_HI/RP_LO/RP_HI를 외부 574 다섯 개로 옮겼다. 기존 여섯 개를 합쳐 **574는 11개**다. DBUS는 ALU A에도 연결되고, ALU 계산 중 선택한 bank 레지스터가 DBUS를 구동한다. MBR은 B, RESULT는 Y를 받는다.

성공한 32 IC 조합은 다음과 같다. 모든 CPLD는 PLCC44, JTAG ON이다.

| 블록 | 역할 | 실제 MC | 일반 I/O / 28 | 전용 입력 / 4 |
|---|---|---:|---:|---:|
| ATF1504 `extseq` | 제어 ROM 주소·다음 상태·opcode 분기·WAIT·HALT | 55/64 | 27 | 4 |
| ATF1504 `tblaux` | 상수·플래그·스택 검사·쓰기 보호·SUB/OE | 53/64 | 28 | 4 |
| ATF1502 `extctrl` | bank 클록 5, bank OE 5, 기존 래치 클록 6 | 27/32 | 24 | 3 |

세 장치 모두 실제 `Design fits successfully`다. 다만 이 성공은 **추가 ROM을 사용하는 기능 배분**에 대한 것이다.

| 부품 | 수량 |
|---|---:|
| 기존 74 ALU | 12 |
| 74HC574 | 11 |
| ATF1504×2 + ATF1502×1 | 3 |
| 프로그램 Flash + SRAM×2 | 3 |
| 제어 ROM | 1 |
| 메모리 디코드 테이블 ROM | 1 |
| 74HC14 | 1 |
| **합계** | **32** |

발진기 모듈, 어댑터·수동부품·메일박스 코프로세서는 제외한다. 이 후보에서 Flash/ROM 세 개는 SST39SF010A로 배정한다. 재고만으로 제작 가능하거나 전역 최소라는 뜻은 아니다.

메모리 디코드 ROM 대신 기존 gate-only 디코더 10개를 쓰면 `extseq + extaux + extctrl` 조합으로 **41 IC**다. 이때 AUX는 52/64 MC, 일반 I/O 27개다. 41개 안에도 제어 ROM은 남는다. 41→32의 9개 감소는 특정 10칩 디코더를 ROM 하나로 바꾼 결과이지, 모든 74 디코더의 최적값과 비교한 결과가 아니다.

32개 후보의 연결표에는 **121개 신호 net, 524개 기능 신호 핀 접점**이 있다. 이는 점퍼선 수나 길이가 아니다. 8비트 ALU A 전용 묶음이 없어져도 래치 제어, ROM 주소선, fan-out이 추가되므로 전체 배선의 우열은 동일 집계 범위에서 따져야 한다.

## 11. fit 성공 뒤 무엇을 실행 검증했는가

[cupl_model.py](cupl_model.py)는 생성 CUPL의 조합식과 D 식을 읽어 같은 클록에서 갱신하고, 외부 574의 상승 에지 캡처를 모델링한다. 고수준 Transfer 실행 함수를 호출해서 정답을 대신 만들지 않는다. 74 ALU는 기존 부품 회로 모델을 사용한다.

기록된 검증은 다음과 같다.

- 540개 opcode/flag·WAIT·stack·PC wrap·재귀·Boot/Run 사례에서 기준 CPU와 명령 완료 상태 및 메모리 접근 주소·값·순서가 일치했다.
- 추가 10개 검사에서 테이블 디코드 ROM, 전체 주소/모드, 쓰기 보호, HALT/오류 뒤 정지, ALU 고장 전파, fixture 재초기화, pad와 연결표를 확인했다.
- DBUS 다중 구동과 캡처 전후 데이터 변화도 검사한다.

이것은 **pre-fit 논리식의 클록 에지 통합 검증**이다. 물리 fitter 이후의 지연 모델은 아니다. 초기 레지스터는 fixture로 주며 **reset-vector를 실제 버스로 읽는 부팅은 아직 미구현**이다. tPD 10 ns를 fitter에 요청한 사실도 보드 전체의 10 ns 경로나 2 MHz 합격을 뜻하지 않는다.

따라서 “작동하는 칩 수”라는 질문에 답할 때는 32개를 **전체 기능 배분이 fit되고 위 기능 모델이 통과한 후보**라고 해야 한다. 전원 투입부터 실제 보드가 동작한 완성품이라고 표현하면 안 된다.

## 12. ATF1502는 필요한가: 같은 인터페이스에서 제거 비교

사용자는 1502를 쓴다고 칩 수나 배선이 확실히 줄어드는지 물었다. 이 질문에 대한 `6eb091a`의 비교는 현재 CMD 6비트, phase 2비트, WAIT 인터페이스와 16개 제어 출력을 유지한 채 1502를 대체한 것이다.

첫 직접 출력 대안은 ROM×2 + 273×2 + 04×1이었다. 이후 배선을 줄인 인코딩형은 다음과 같다.

- ROM×1: 512바이트 표, 명령·phase·WAIT를 입력으로 사용.
- HC273×1: 쓰기 목적지 4비트, 캡처 1비트, 읽기 소스 3비트 저장.
- HC238×2: 11개 래치의 양극성 클록 생성.
- HC138×1: bank의 음극성 OE 5개 생성.
- 기존 HC14의 남는 게이트 2개 사용: 패키지는 추가하지 않음.

| 동일한 전체 후보 기준 | 1502 사용 | 인코딩형 대체 | 1502를 쓸 때 감소 |
|---|---:|---:|---:|
| IC | 32 | 36 | 4 |
| 고유 신호 net | 121 | 139 | 18 |
| 기능 신호 핀 접점 | 524 | 565 | 41 |

직접 출력 대안은 143 nets/579 접점으로 55 접점 차이였지만, 개선한 인코딩형과의 최종 차이는 **41 접점**이다. 두 수치를 섞지 않는다.

512개 입력 조합의 다음 출력, 256개 레지스터 출력값에 대한 실제 디코더 연결을 비교했고, 재귀·WAIT·MMIO·스택 오류를 포함한 10개 테스트 통과가 기록되어 있다. 디코더의 아날로그 글리치·전파 지연은 검증하지 않았다.

이 비교에서 1502는 부품과 내부 제어 연결을 줄인다. 하지만 **1502가 기능상 반드시 필요하다거나 다른 재분할에서도 항상 4개를 줄인다는 증거는 아니다.** 두 1504의 현재 일반 I/O 합은 55/56이어서 16개 출력을 그대로 옮기기는 어렵지만, 인터페이스와 FSM을 함께 재설계하는 대안은 별도 탐색 대상이다.

특히 대체안의 ROM 한 개는 기존 프로그램 ROM·제어 ROM·디코드 ROM과 별개로 추가된다. ROM을 허용하지 않는 비교에 이 결과를 그대로 적용할 수 없다.

## 13. “ROM이 왜 들어가나요”: 숨겨졌던 전제 명확화

사용자의 “RON이 왜 들어가나요”는 직전 문맥에서 ROM에 대한 질문으로 해석되었다. 이 시점에서 세 ROM의 역할을 분리해 설명했다.

| ROM | 저장 내용 | 도입 목적 |
|---|---|---|
| 프로그램 ROM/Flash | CPU가 실행할 프로그램 | 기존 메모리 구성 |
| 제어 ROM | 전송 명령과 다음 상태 | 큰 CU 상태 전이표를 CPLD 밖으로 이동 |
| 메모리 디코드 ROM | 주소/모드별 CE | 10칩 gate-only 디코더 대체 |
| 1502 제거안의 추가 ROM | 출력 인코딩 표 | 1502 제어 출력의 대체 회로 구성 |

제어 ROM은 2 KiB 이미지다. 상태마다 명령·분기 모드, 두 후속 상태의 하위 바이트, 후속 상태 상위 비트를 네 바이트로 저장한다. 주소는 uPC 9비트와 phase 2비트의 11선이며 DBUS를 공유한다.

디코드 ROM은 A2..A15와 MAP의 15비트 주소에 대해 32 KiB 표를 만들고 RAM0/RAM1/program-ROM/mailbox CE를 출력한다. 실제 WE는 AUX가 쓰기 구간과 ROM 선택을 조합하여 제한한다. 디코드 ROM을 제거하는 문제와 제어 ROM을 제거하는 문제는 다르다.

정정된 결론은 다음과 같다. **32개 fit 성공은 “추가 ROM 두 개를 허용한 구성”의 결과다. 74 ALU·외부 래치·1504 두 개·1502 한 개만으로 CU를 해결한 결과가 아니다.** 이 전제를 칩 수보다 먼저 밝혔어야 했다.

## 14. ROM 속도 우려와 FSM 축소 방향

마지막 기술 질문은 “FSM을 줄이는 다른 방법 없나요 ROM은 인출 속도가 떨어질거 같아 보이는데”였다.

현재 [rom_search.py](rom_search.py)는 전송마다 제어 ROM을 네 번 읽고, 실제 전송에 다시 네 phase를 사용한다. 따라서 WAIT 없는 일반 전송은 **4→8 tick**이다. 같은 클록에서 전송 처리율이 절반이 되는 구조다. HALT·WAIT 등 경계 비용이 있으므로 모든 프로그램의 MIPS가 정확히 절반이라고 일반화하지 않는다. 또한 이는 현재 직렬 인출 방식의 비용이지 모든 ROM 제어기의 필연적인 비용은 아니다.

### 14.1 현재 상태 수가 커진 이유

[cu_fsm.py](cu_fsm.py)의 `Graph.add()`는 `(transfer, successor)`가 모두 같을 때만 노드를 합친다. 같은 전송이어도 복귀할 위치가 다르면 별도 상태가 된다. 공통 suffix는 합치지만 공통 절차를 호출하고 돌아오는 구조는 아니다.

현재 그래프를 집계한 결과는 다음과 같다.

| 집계 | 값 |
|---|---:|
| 전체 상태 | 292 |
| 서로 다른 전송/종료 표식 | 43, HALT용 `None` 포함 |
| 서로 다른 opcode 진입점 | 14 |
| `MBR ← 1` 전송이 나타나는 상태 | 65 |
| PC_LO의 ALU→RESULT 전송 상태 | 28 |
| RESULT→PC_LO 전송 상태 | 28 |
| PC_HI의 ALU→RESULT 전송 상태 | 28 |
| RESULT→PC_HI 전송 상태 | 28 |

대화에서 “서로 다른 전송 동작 43종”이라고 간단히 표현했지만, 정확히는 정지 표식 하나를 포함한 수다. 이 수치를 곧바로 43상태 FSM 가능성이나 MC 사용량으로 바꾸면 안 된다. 순서, 호출 위치, 분기와 피연산자 선택을 기억할 추가 상태가 필요하다.

### 14.2 ROM 없는 후보의 구체적 축소 축

첫 번째는 **PC/RP 증감 절차의 공유**다. PC/RP 선택, 증감 방향, 필요한 상수, 끝난 뒤 이어갈 위치를 기억하고 연산 절차는 한 벌만 둔다. 저위 바이트 carry/borrow에 따라 상위 바이트를 처리하는 구조도 공유 대상으로 삼는다.

두 번째는 **명령 종류와 실행 단계를 분리**하는 것이다. 명령마다 전체 경로를 펼치는 대신 명령 class, 단계 카운터, 하위/상위 바이트 선택으로 제어한다. 피연산자 바이트 인출도 같은 절차를 반복하도록 구성할 수 있다.

세 번째는 **CALL/RET 공통 절차 공유**다. RP 읽기·검사·주소 설정·최종 RP 저장을 공유하고, CALL/RET에 따라 메모리 방향과 PC/TMP 소스를 선택한다. 잘못된 RP에서 쓰기 전에 멈추는 동작은 그대로 유지한다.

이 변경은 버스 공유와 74 ALU를 유지하면서 CU의 중복 전개를 줄이려는 방향이다. 복귀 정보 저장과 선택 논리가 추가되므로, 상태 개수 감소가 같은 비율의 MC 감소나 클록 개선을 보장하지는 않는다. 중첩 호출을 피하는 단계 설계, 복귀 selector 폭, 제어 출력 인코딩을 함께 검토해야 한다.

### 14.3 여기까지 확인된 것과 아직 없는 것

현재 코드는 반복 상태가 많다는 근거를 제공한다. 그러나 **공통 절차형 ROM-free CU의 생성 CUPL, vendor fit 결과, 통합 실행 결과는 아직 없다.** 1504 두 개와 1502 한 개에 수용된다고 확정하거나 새 칩 수를 제시할 단계는 아니다.

최근 논의의 우선 방향은 추가 제어 ROM으로 문제를 넘기기 전에 FSM을 구조적으로 줄이는 것이다. 사용자가 모든 종류의 ROM을 전면 금지했다고 기록하지 않는다. 프로그램 ROM, 제어 ROM, 디코드 ROM을 구분하여 인출 비용과 자원 절감을 따로 비교해야 한다.

## 16. 이어서 연구할 때 유지할 조건과 평가 순서

후속 연구는 현재 ISA, 비중첩 순차 실행, 공통 8비트 hi/lo 버스, 기존 12칩 74 ALU, 단순 외부 래치를 유지하는 조건에서 시작한다. CPLD 보유량은 1504 두 개와 1502 한 개다. 칩 수를 줄이기 위해 메모리 접근 순서, WAIT 부작용, 스택 오류 처리를 누락하지 않는다.

ROM-free FSM 후보를 연구할 경우 필요한 산출물은 다음 순서다. 이는 다음 실험의 평가 기준이며, 이번 문서화에서 이미 구현했다는 뜻은 아니다.

1. 공통 절차·명령 class·단계·복귀 selector를 명시한 실행 모델을 만든다.
2. 모든 opcode, PC wrap, carry/borrow, CALL/RET 경계, Boot/Run, MMIO, WAIT에서 기준 상태와 메모리 순서를 비교한다.
3. CPLD별 책임과 신호 방향을 정하고 CUPL을 생성한다. MC뿐 아니라 일반 I/O, 전용 입력, JTAG 예산을 함께 센다.
4. 실제 vendor fitter로 수용 여부를 확인한다. 실패 통계와 성공 통계를 구분한다.
5. 생성된 논리식과 외부 래치·74 ALU를 통합 실행한다. 부팅 초기화도 별도 완료 항목으로 둔다.
6. 외부 디코더·인버터·래치·메모리·클록 보조 부품까지 포함한 같은 범위의 BOM과 연결표를 생성한다.
7. 프로그램별 전송 수와 tick을 다시 측정하고 같은 가정 클록에서 비교한다. 이후 실제 지연·부하·setup/hold를 검증한다.

아직 남은 공통 항목은 reset-vector 실제 버스 부팅, post-fit 또는 이에 준하는 타이밍 검증, 전원 투입·리셋·WAIT 회로, 보드 배선과 팬아웃, 실측 동작 클록이다. 이 항목들을 수행하기 전까지 실물의 “완성 동작”과 기능 시뮬레이션을 분리한다.
